## 一、背景与原型问题陈述

### 1.1 为什么做这个主题

第 26 套效果要补的不是"又一种粒子"，而是**库里唯一缺失的一类运动语义：群体**。
现有 25 套里，运动的主体要么是**单个物体**（E29 行星 / E35 光轴 / E42 星轨）、
要么是**介质本身**（E43 海浪 / E46 雾 / E47 雪 / E48 烟），
⛔ **没有一套的主体是"一群互相影响的个体"**——而这是自然界最常见的运动形态之一，也是最容易
在电视上被一眼认出的形态（**murmuration**，椋鸟暴群）。

所有者需求的四条原话口径与其推论：

1. **狂野气质**：宽银幕、天空压倒性、地面极窄、地平线极低、运动尺度大。
   ⇒ 构图上天空占绝大部分，**地面只占底部 1/5**。
2. **地平线固定 + 地面/草丛极缓慢横向视差漂移**。
   ⇒ 地平线是**锚**，不是被鸟带着跑的构图元素；横向漂移只发生在底部 1/5 的带里。
3. **用 Boids 模型仿真鸟群飞翔**（Reynolds 1987）。
   ⇒ 运动由**规则**产生，不由时间轴关键帧产生；这条决定了整份文档的 §四 与 §七。
4. **鸟用动态剪影即可，不要求精细绘制** + **部分鸟会停树后再起飞**。
   ⇒ 剪影 + 状态机（飞行 / 停栖 / 再起飞），⛔ 不做骨骼动画、不做逐帧贴图序列。

### 1.2 ⛔ 与 E47 / E48 的构图区分点（⛔ 三套不能互相"读成同一张图"）

| | **E47 雪松** | **E48 大漠** | **E49 鸟群（本主题）** |
|---|---|---|---|
| 构图重心 | 中右一棵**贯穿上下**的大树 | **低垂日盘 + 多层沙丘脊** | **天空**（鸟群是主体，画面本体在 3/4 画幅以上） |
| 地面占比 | 下半屏雪原 | 约 2/5 沙丘 | **底部 1/5** |
| 时间性 | 雪**恒定下落**（静物 + 恒定现象） | 烟**单向摆动 + 驼队偶发** | 群体**自组织运动**（无周期、无编排） |
| 叙事 | 「站在树下避雪」——**人的静止** | 「大漠孤烟直」——**物的静止 + 偶尔的人** | 「一群鸟掠过，停一停，再飞走」——**群体的来去** |
| 第一读感 | 冷 / 静 / 垂 | 暖 / 静 / 竖 | 开阔 / 动 / 横 |

⭐ **关键区分点只有一条，其余全是它的推论**：**E47 是雪景静物、E48 是沙丘孤烟，两者都是
"大面积静的东西 + 一点点动的东西"；本主题是唯一一套"动的东西本身占主体"的**。
⇒ 因此三条硬性后果：
- ① 天空必须**空到能承载运动** ⇒ ⛔ 不画日盘（否则与 E48 的第一读感撞车）、
  ⛔ 不画云团（会变成"背景物体"抢主体）、⛔ 树必须少而暗（只在底部带里）。
- ② 地面带必须**窄**且**低对比** ⇒ 它的作用是给运动一个参照速度（视差），⛔ 不是风景。
- ③ 运动必须**成群**，不能是"一堆各自乱飞的鸟" ⇒ 这直接推出 §四 的全部规则与 §八 的 γ 判据。

## 二、概念图与设计语言

### 2.1 色调：暖色荒野 vs 冷色雪景的取舍

- **冷调被排除**：`SEASIDE`(43)/`SNOW_CEDAR`(47)/`TRIPOD_FOG`(46) 已经是冷色三连。
  再来一套冷色 + 无日盘 ⇒ 在缩略图上与「雪松」不可分。
- **暖红落日被排除**：`DESERT_SMOKE`(48) 的第一读感就是"低垂巨大落日 + 无云暖红天空"，
  ⛔ 本主题**不画日盘**（§1.2 ①）。
- ✅ **选定：黄昏前的清冷高调天 + 暖色地面**。天空**顶部偏冷**（暮色的蓝紫灰，
  但**不是 E48 那种饱和红**），**地平线附近最亮**；暖色全部落在**地面带与树**上。
  ⇒ 结果是**鸟的深色剪影压在中间调天空上**，对比最强、剪影最可读 ——
  这正是 §二.3 那条明度层次要服务的第一目标。

⚠️ 这条与 E48 的**暖色**只共享"色温族"不共享"读感"：E48 的暖来自**一个发光物体**（日盘），
本主题的暖来自**被低角度光照的地面**。判读时的具体色值由原型 + 参考图 gate 定，
⛔ 本阶段不写 RGB 数字（§八 R9）。

### 2.2 天空渐变与构图锚点

```
horizonY = 0.800 · H                    // ⛔ 地平线固定，不由鸟群位置决定（需求 ②）
skyTop L ≈ 0.13 … 0.18                  // 暮色天顶：偏冷，⭐ 比 E48 的天顶（L≥0.13）更亮
skyMid L ≈ 0.28 … 0.34                  // 中段：鸟群主要活动带，压最暗的剪影
skyHorizon L ≈ 0.62 … 0.72              // 地平线上方最亮的一段（大气散射）
```

- **3 锚点竖向渐变**（天顶 / 中段 / 地平线），⛔ 不画任何形状图元（无云、无日盘、无光柱）。
- ⛔ **不做逐帧渐变**：`createLinearGradient` 逐帧调用是全仓库已定的红线（E43 §4.9.2 把 97 个
  逐列渐变折成一条 Path + 一支缓存竖向渐变）⇒ 本主题的天幕**整幅烘进一张位图**，逐帧 1 次 blit。
- **地面带** = `0.800H … 1.00H`（**恰为 1/5 屏**，需求 ① 的量化落点），暖褐色，
  带极轻微的大尺度明暗起伏（⛔ 不画草叶细节，草在近景另有一层）。
- **地平线是一条直线**（需求 ②「地平线固定」）—— ⛔ 这一点与 E47 的 P16/E48 的 P8 是**相反**的：
  E47/E48 的地平线**不能**有"尺子线"（因为它们的地面是有起伏的地形）；
  本主题的地面是**极窄的带**且**极低对比**，一条干净的直线正是"远景"读感的来源。
  ⇒ 移植时 ⛔ 不得照抄 E47「沿雪面裁掉位图直边」那套做法。

### 2.3 剪影的明度层次（本主题最重要的一条可读性契约）

- 鸟分 **4 个飞行深度层**（+ 1 个停栖层），**越远越淡、越偏天空色**（大气透视）：
  ```
  layer 0（最远）  α 低、色 = mix(skyMid, ink, 0.28)
  layer 1          α 低、色 = mix(skyMid, ink, 0.46)
  layer 2          α 中、色 = mix(skyMid, ink, 0.68)
  layer 3（最近）  α 高、色 = ink（最深）
  perched（停栖）  α 高、色 = ink（与最近层同深；⛔ 不比 layer 3 更深，见下）
  ```
- ⛔ **同层内所有鸟的 α 与色必须相同**。逐鸟随机 alpha 会让整群读成**噪点**，
  而"一群深度一致的鸟"本身就是 flocking 正确的**视觉证据**（这与 E48 P18「逐列阈值分支 = 梳齿」是同一条纪律的另一个应用面）。
- ⛔ **停栖鸟不得比飞行鸟更深**：更深 ⇒ 读成"树上长了黑疙瘩"而不是"鸟停在树上"。
- 树的剪影比鸟**更深但更矮**（树在底部带里，尺度受限）；树的深色是**给鸟当背景锚**用的，
  ⛔ 不与鸟争主体。
- 侧倾是鸟身上**唯一的姿态信息**（因为不做精细绘制）⇒ 侧倾的可见性是硬需求（§八 R3）。

### 3.1 Reynolds 1987（SIGGRAPH）与他的 1986 年 Lisp 原码

- **论文**：「Flocks, Herds and Schools: A Distributed Behavioral Model」，
  SIGGRAPH '87 / *Computer Graphics* **21(4), 25–34**。⚠️ 方案早期版本误写标题为
  "Segmented Behavior for Unnatural Animals"、卷期为 21(2)，2026-10-15 已按 O7 核对订正。
  三规则（**分离 / 对齐 / 聚合**）+ 一个
  **不依赖任何全局变量的局部规则集** ⇒ 群体行为**涌现**而非编排。
- **书目（§十四 O7）**：Reynolds, C. W. (1987). *Computer Graphics*, 21(4), 25–34
  （ACM SIGGRAPH '87 Conference Proceedings, Anaheim, July 1987）. DOI: 10.1145/37402.37406
- ⭐⭐ **最有价值的一手物证是 boids.lisp（1986）原码本身**，不是论文：
  那份代码里的常数是**他反复调出来的真实观感值**，而且**注释里保留着他否掉的备选值**
  （"原来是多少、为什么换掉"）。这是**唯一**能回答"分离权重该比对齐大多少"的实证来源 ——
  论文正文只给伪代码，伪代码里的参数全是符号。
- ⚠️ **纪律**：`boids.lisp` 的常数表（§4.3）是本方案唯一一处"允许出现具体数值"的外部常量表，
  但它必须**逐条抄核原文**后填入，并作为 harness 的一次性输入。
  ⛔ **不得凭本方案的转述直接落 Kotlin**（本节转述的每一条都带 `⟨待原文核对⟩`）。

**对实现的三条硬约束**（都出自论文正文，不需要抄数）：
1. ⛔ **不能用"朴素加权平均"**（§4.1 详述 Reynolds 的两条批评）。
2. steering 必须是 `desired − velocity` 的**间接式**，⛔ 不是直接设定 velocity。
3. **加速度**（steering 之和）必须先**截断**到 `maxForce` 再累加，⛔ 不是先累加再截断。

### 3.2 Ballerini et al. 2008：真实椋鸟是**拓扑** flocking，不是固定半径

- 实测：每只椋鸟的拓扑邻居数 **n_c = 6.5 ± 0.9**（与密度、与群体规模**无关**）。
- 指标半径 flock（metric）在扰动下会**碎裂**（split into subgroups），
  拓扑 flock 则不会 ⇒ 这不是"拓扑更优雅"，是"真实鸟就是这么做的"。
- ⇒ **对本方案的直接约束**：邻居判定用 **top-7**（§4.5），
  ⛔ 不得实现成"半径 R 内的全部邻居"。半径只作为**搜索加速的空间哈希格子尺寸**，⛔ 不是选择判据。
- **书目（§十四 O7）**：Ballerini, M., Cabibbo, N., Candelier, R., Cavagna, A., Cisbani, E., Giardina, I.,
  Lecomte, V., Orlandi, A., Parisi, G., Procaccini, A., Viale, M., & Zdravkovic, V. (2008). Interaction ruling
  animal collective behavior depends on topological rather than metric distance: Evidence from a field study.
  *Proceedings of the National Academy of Sciences*, 105(4), 1232–1237. DOI: 10.1073/pnas.0711437105

### 3.3 StarDisplay（Hemelrijk, van Zuidam & Hildenbrandt 2015）：椋鸟骚动波是**侧倾波**，不是密度波

- 暴群里肉眼可见的"暗色波浪"传过群体，其机制是 **banking wave（侧倾波）**，
  ⛔ **不是**局部密度涨落（密度波会给出完全不同的观感）。
- **滚入比滚出快**（倾角建立快、回复慢）⇒ 侧倾是**非对称**的。
- **侧倾导致掉高度**（真实椋鸟转弯时下沉）——⭐ **本方案刻意不实现这一条**：
  在**剪影**表现下，侧倾一旦带掉高度，鸟群会**读成鱼群**（鱼靠摆尾+下沉转向）。
  ⇒ 只实现"看得见的倾角"，⛔ 不实现"看得见的高度损失"。
  ⚠️ 这是本主题最容易被"顺手加上去"的一条 ⇒ 单列为开放项 O4。
- **书目（§十四 O7）**：① 骚动波=侧倾波结论出自 Hemelrijk, C. K., van Zuidam, L., & Hildenbrandt, H. (2015).
  What underlies waves of agitation in starling flocks. *Behavioral Ecology and Sociobiology*, 69(5), 755–764.
  DOI: 10.1007/s00265-015-1891-3（⚠️ 第一作者是 Hemelrijk；方案早期版本误标 "Hildenbrandt et al."，已订正）；
  ② **StarDisplay 模型本身的原始出处**：Hildenbrandt, H., Carere, C., & Hemelrijk, C. K. (2010).
  Self-organized aerial displays of thousands of starlings: a model. *Behavioral Ecology*, 21(6), 1349–1359.
  DOI: 10.1093/beheco/arq149（§4.5 的 k≈6~7 若要引 StarDisplay，应引此篇）。

### 3.4 Tobalske 2001：爬升 / 起飞时**振幅与频率同步上升**（振幅调制）

- 椋鸟在**爬升与起飞**段，翼的**振幅与频率同时上升**；
  在**巡航滑翔**段则切换为 flap–glide 交替（bound gait）。
- ⇒ **对本方案的直接约束**：扑动**不能**是一个全程恒定的正弦。
  本方案取**两个调制量**：① 爬升/起飞段的 `flapFreq↑` + `flapAmp↑`（两者同时）；
  ② 巡航段的 flap / glide **二态交替**（滑翔时 `flapAmp = 0`、翼后掠成一条直线）。
  ⛔ 只做频率变化而振幅恒定 ⇒ 读成"机关鸟"。
- **书目（§十四 O7）**：Tobalske, B. W. (2001). Morphology, velocity, and intermittent flight in birds.
  *American Zoologist*, 41(2), 177–187（DOI 未在馆藏记录中核对，故不写）。⚠️ 核对注：本节的
  **巡航 flap–glide 交替**论断与这篇综述的主题（intermittent flight / bound gait）吻合；
  **爬升/起飞段振幅-频率同步上升**若需精确出处，须另查 Tobalske 的起飞动力学文献
  （不属于本方案开发阻塞；如需补条目，由所有者 O7 追加记录）。

### 4.1 三规则的 steering 间接式（⭐ 逐条照抄 Reynolds 对"朴素平均"的两条批评）

Reynolds 在论文正文里明确批评了"把三条力的结果加权平均"这种朴素做法，给了两条理由：

```
desired   = 归一化的(邻居均值 − 自身位置)   // 或邻居平均速度
steer     = clamp(desired − v, |steer| ≤ maxForce)      // ⛔ 间接式
// 加权平均（朴素做法，错）：
//   steer = (wSep·sep + wAli·ali + wCoh·coh) / (wSep + wAli + wCoh)
```

1. **相反方向的加速度请求会互相抵消**：一群鸟想散开（分离）在数学上是负向力，
   想聚合是正向力。平均之后**净结果接近零** ⇒ 鸟群"原地呼吸"一下就僵住。
   → 正确做法是**优先级累加**：先分离（安全），再对齐，再聚合（聚合**最弱**），
   累加后**整体**再截断到 `maxForce`。
2. **平均法会编造出"谁都没建议过的航向"**：三个方向的请求平均之后得到一个**中间方向**，
   而这个方向**没有任何一条规则提出过**。真实群体里不会出现这种"投票折中航向"。
   → 正确做法是每条规则先各自算 `desired`，**统一走同一个 `desired − v` 形式**，
   ⛔ 不得把三条 steer 先平均。

```
steerTotal = truncate(steerSep + steerAli + steerCoh, maxForce)
v          = clamp(|v + steerTotal·dt|, |v| ≤ maxSpeed_i)      // 逐鸟 maxSpeed（§4.10）
p          = p + v·dt
```

⚠️ **截断的位置有讲究**：`desired − v` 本身**不截断到 `maxForce` 之前的中间量**必须先限幅，
否则一次邻居骤变会给出巨大的 steer。⇒ 实现顺序固定为：
**① 每条规则各自的 `desired` 归一化 → ② 每条规则各自的 `steer` 截断到 `maxForce` →
③ 优先级累加 → ④ 累加结果再截断到 `maxForce`**（§四 的 T1 判据就钉这个顺序）。

### 4.2 分离项的**有界形式**（boids 爆炸的头号来源）

论文正文用的是平方反比直觉，但裸 `1/d²` 在两鸟重合时**发散**：

```
⛔ 裸形式：  sep = −(Σ_j  (p_j − p_i) / d_ij² )      // d → 0 时 → ∞ ⇒ 一帧内 NaN/爆炸
✅ 有界形式：sep = −(Σ_j  (p_j − p_i) · (1 − d_ij/R)^n / d_ij )      // n ∈ [1, 3] ⇒ **原型实证 n = 2**
             // (1 − d/R)^n 在 d = R 处为 0、d = 0 处为 1 ⇒ 平滑有界

- ⭐ **原型实证（2026-10-14）**：`steerBoids()` 用 `guard = (1 − d/sepR)^2`（HTML `Math.pow(1-rd,2)`），
  `sepR = 38px`。n = 2 在 200/400/600 三档下 T4（NaN）= 0、T5（冻结）= 0，无爆炸迹象 ⇒ **Kotlin 直接采用 n = 2**。
  ⛔ 不改 n 或 sepR 时必须同步重跑 T2 负样本（去掉守卫 ⇒ NaN/Inf 帧 > 0）。
```

- `(1 − d/R)^n` 就是那个**守卫因子**：它把 `1/d` 的奇点在 `d = R` 处截平。
- ⛔ **必须同时有 `1/d` 与守卫**：`1/d` 保证近处推力随距离增强，`(1−d/R)^n` 保证有界。
- ⚠️ `R` 必须吃**逐鸟的感知半径**（§4.5），⛔ 不能是全局常数。
- **退化测试（T2 的负样本）**：把守卫去掉 ⇒ harness 必须在 5400 帧内报出 NaN/Inf 帧 > 0。
  ⛔ 一条"永远绿"的分离项判据没有牙齿。

### 4.3 Reynolds 的实际常数表（boids.lisp）与它的**刻意不对称**

> ⚠️⛔ **本表的每个数值都必须在定稿前从 `boids.lisp` 原文逐条抄核**（见 §3.1 的纪律）。
> 现在写在这里的是**待核对位**，⛔ 不得直接落 Kotlin。

| 参数 | 含义 | 本方案取值 | ⛔ 备注 |
|---|---|---|---|
| `maxSpeed` | 巡航速上界（归一单位） | `⟨待原文核对⟩` | 逐鸟乘以 `cruiseK`（§4.10） |
| `maxForce` | 单次 steering 的幅值上界 | `⟨待原文核对⟩` | ⛔ 它与 `maxSpeed` 的**比值**才是旋钮（§4.4） |
| `wSep` / `wAli` / `wCoh` | 三规则权重 | `⟨待原文核对⟩` | 结构事实：**分离 ≫ 对齐 ≳ 聚合**；聚合最弱 |
| `neighborRadius` | 指标半径 | `⟨待原文核对⟩` | ⛔ 在本方案里它只是**搜索格子尺寸**，⛔ 不是选择判据（§3.2） |
| `separationRadius` | 分离半径 | `⟨待原文核对⟩` | 比 `neighborRadius` **小** ⇒ 只推开真正近的 |
| ⭐ `anti-climb` | 上边界（爬升越界）的回推系数 | **0.1** | ⛔ **刻意不为 0** |
| ⭐ `anti-dive` | 下边界（俯冲越界）的回推系数 | **0** | ⛔ **刻意为 0** |

⭐⭐ **上 0.1 / 下 0 的不对称是 boids.lisp 里最容易被"顺手抹平"的一条**：
代码里 `anti-climb = 0.1` 而 `anti-dive = 0`，**不是笔误，是他的选择** ——
下边界不需要推力（鸟本来就不愿往下钻），而上边界的"不许继续爬"必须存在，
否则群会自己爬出画面。本方案照抄这组不对称，并把它写进 §4.7 的软约束表。
⚠️ T3 判据就钉这一条：**`antiDive == 0` 且 `antiClimb > 0`**；
负样本 = 把 `antiDive` 也设成 0.1 ⇒ 当场变红（后果见 §八 R4）。

### 4.4 `maxForce / maxSpeed` 比值 = 最小转弯半径 `v²/a`

```
r_min = v_max² / maxForce          // ⛔ 单位系；maxForce 越小 ⇒ 转弯半径越大 ⇒ 弧线越宽缓
```

- 这是**「宽缓弧线」还是「darting 鱼群」的总旋钮**：
  - `r_min` **大**（`maxForce` 小）⇒ 鸟转不过急 ⇒ 群是一大片**宽缓的涡**，
    但 ⚠️ 代价是**群体的灵活性下降**（会撞上边界、跟随不出急转弯）。
  - `r_min` **小**（`maxForce` 大）⇒ 每只鸟都能急转 ⇒ 读成**鱼群 / 一堆乱窜的粒子**。
- ⇒ 本方案把它写成**一个可扫描的一维旋钮** `turnR`（以 `r_min / birdLen` 为单位）；
  ⛔ **HTML 未实现显式 r_min**（下注）⇒ Kotlin 侧实现后由 T4 区间判据 + 负样本锁死。
- ⚠️ **原型偏差（必须迁移时对齐）**：HTML 的 P 表有 `turnR: 26` 与滑杆，但 `steerBoids()` **从未消费它**——
  转弯尺度实际由「④ 再截断到 `maxForce`」（`accelCap = spdN·speedK·respK·5.5`）+ 后续 `spdMax` 速度钳制共同决定，
  ⛔ **没有实现 §4.4 的 `r_min = v²/a` 显式语义**。⇒ Kotlin 侧二选一：
  **① 实现真正的 `r_min` 旋钮**（推荐，§4.4 的宽缓弧线 vs darting 鱼群的总旋钮才有意义）；
  **② 照抄 HTML 的近似**并存档为“已接受近似”。两者都必须先在 harness 里用 T4 区间判据 + 负样本锁死。
- ⭐ **它在剪影上的表现特别关键**：倾角 `φ = atan2(a_lat, g)`（§4.9）只吃**横向加速度**，
  所以 `r_min` 一变，**整个群体的倾角读感就全变了** ——
  ⛔ 不要在 `φ` 公式里另加一个"看起来更倾"的系数去补偿（那会破坏 §4.1 的单一来源）。

### 4.5 拓扑邻居上限 `k = 7`（Ballerini / StarDisplay 都落在 6~7）

```
candidates(i) = 空间哈希的 3×3 邻格内、逐格容量上限 C 的鸟
neighbors(i)  = candidates 中按 (d² , index) 取**最近 k = 7 只**     // ⛔ 不是"半径内全部"
⇒ 每只鸟只看 7 只 ⇒ 每帧邻接计算量与群体规模**解耦**
```

- `k = 7` 直接对应 §3.2 的 `n_c = 6.5 ± 0.9`。
- ⛔ **取 top-k 必须有确定的 tie-break**（`d²` 相等时按 index）⇒ 否则同一次运行的
  邻居集不可复现，harness 的"逐位复现"判据会随机变红。
- ⚠️ **容量上限 `C` 是双刃剑**：`C` 太小会**系统性漏掉更近的邻居**（格子按插入序填满 ⇒
  先插入的偏得）。⇒ harness 必须出一条判据：
  **`k` 满编率**（实际取到 7 只的鸟的比例）**且** `C` 放宽一档后结果稳定（自洽性）。
  ⛔ 只报"平均邻居数 6.8"会掩盖"某处其实只取到 2 只"。

**原型实证（2026-10-14/15）**：
- 邻居均值：LOW **5.9** / MED **6.5** / HIGH **6.7**（T7，均落在 3~7 区间，与 §3.2 的 n_c = 6.5±0.9 同量级；
  HTML 已按 §8.3 B2 改为纯拓扑 top-7，2026-10-15 三档重跑（G 轮鸟数下调 300/800/1500 → 200/400/600）后实测值整体下移）；
- 容量上限 `C`：LOW 14 / MED 16 / HIGH 18（`TIERS.gridCellCap`），格子宽 = `max(40, nbrR·1.2)` px；
- ⚠️ **实现偏差（Kotlin 迁移时必须决策）**：HTML 的 `findNeighbors()` 实际是
  **半径过滤（`d² < nbrR² = 60px`）∩ 前向锥（dot > 0）内取 top-7**，⛔ 与 §3.2 的
  “半径只作搜索格子尺寸、不作选择判据”的纪律**不一致**（`nbrR` 同时充当了候选过滤条件）。
  效果上三档都健康（邻居均值达标、无冻结），但大群边缘可能因此漏选更远的真实邻居。
  ⇒ Kotlin 侧应实现**纯拓扑 top-7**（3×3 邻格全部候选按 d² 取最近 7），并在小 N 下与暴力
  O(N²) 交叉验证（§11.2 `BirdsFlockGridTest` ②）；若因格子尺寸漏邻居，优先加大格子而非放开半径过滤。

### 4.6 前向锥视场（解决对称死锁）

```
dot(r_ij, v_i) > 0   且   angle(r_ij, v_i) ≤ θ_cone        // θ_cone 量级 120°–150°

- ⚠️ **原型实证值 = 90° 半平面**：HTML 只用 `dot(r_ij, v_i) > 0`（`dxj·vnx + dyj·vny > 0`），
  ⛔ **没有 θ_cone 参数**。三档实测 T5（冻结帧）= 0、邻居均值达标 ⇒ 90° 锥 + §4.2 有界分离
  已经足够破对称死锁。⇒ **Kotlin 采用 90° 前向半平面**（比 120–150° 更简单且已实证），
  ⛔ 若日后放宽锥角，T5 负样本（锥角 360° ⇒ 冻结上升）必须仍有效。
```

- **要解决的死锁**：A 想躲 B、B 想躲 A，且两者速度对称 ⇒ 双方净力为零 ⇒ **双双冻结**。
- 原理：把"我看得见的邻居"偏向**前方**，则对称局面下至少有一方先动 ⇒ 死锁破。
- ⚠️ **锥角是双刃**：太窄 ⇒ 群尾变成盲区、群体分裂；太宽 ⇒ 死锁回归。
- ⭐ **真正的死锁破法是 §4.2 的有界分离**（它对"贴住"这一情形给一个**非零的切向分量**），
  锥视场是**放大器**不是主角。⇒ T5 判两件事：
  **① 冻结帧数**（`maxSpeed` 连续 `⟨n⟩` 帧低于阈值）**且 ② 冻结时的邻接形状**，
  负样本 = 把锥角拉到 360°（等价于无锥）⇒ 冻结帧数必须上升，否则这条判据没牙齿。

### 4.7 软约束：切向力必须强于内向力（否则"贴墙"）

本主题有两层边界：**硬边界**（不许飞出画幅）与**软带**（画幅内偏好的活动带）：

```
n        = 边界的外法向（指向界外）
d        = 到硬边界的**带符号距离**（负 = 在界内）
hard     = (d < 0) ? n · kHard : 0                  kHard = 2.5   // ⭐ HTML 实测 = 2.5
softPull = smoothstep(bandOuter, bandInner, d) · (指向带心) · kSoft   kSoft = 1.2   // ⭐ HTML 实测 = 1.2
tangent  = normalize(v − (v·n)n) · kTangent                    // 沿边界的滑移分量  // ⭐ HTML 实测 = 0.7
```

- ⭐ **原型实证（2026-10-14）**：`kHard = 2.5 / kSoft = 1.2 / kTangent = 0.7` 与 §4.7 设计目标**完全一致**
  （P 表直读）。实现细节两处与公式有出入、Kotlin 迁移时必须决策：
  ① HTML 的软带回拉是**简化的 y 向线性项** `sty -= dyc·P.kSoft·0.0008`（⛔ 不是 smoothstep(bandOuter, bandInner) 双带）；
  ② HTML 的切向滑移**只在 `x < bandN` / `x > W−bandN` 两条竖边**触发（`vy += ±kTangent·0.04`），
  ⛔ 没有 y 向切向（注释说明：原 y 向切向块把中线以下全部吞掉、是贴墙帮凶，已删）。
  ⇒ Kotlin 照 §4.7 的公式实现完整版，但**保留 x 向切向、不恢复 y 向切向**（有实测反例背书）。

⭐ **硬约束 `kHard = 2.5 > kSoft = 1.2` 不是"硬更强所以对"，而是它保证滑移能赢**：
在鸟被压向边界时，它的速度分量分解成 `{内向法向, 切向}`。
若**内向法向占优**，鸟的速度方向垂直于边界 ⇒ 每帧减速度都吃在法向上 ⇒
**贴墙**（鸟沿边界停住、抖动、或堆成一团）⇒ 这就是"贴壁"读感的成因。
⇒ **正确终态是：鸟沿边界滑过去，而不是停在边界上。**
判据形态：**贴壁比例** = 「`|v·n| < ε` **且** 切向速度 `< ε`」的时长占比，
必须接近 0（§十 的数字项之一）；负样本 = 把 `kTangent` 设为 0。

⭐ **可移植的一句话**：任何"边界力"系统都必须显式区分
**法向回推**（阻止越界）与**切向滑移**（允许继续运动），
且**在边界附近切向必须仍有非零速度**，否则约束系统自己制造出"停住"。

### 4.8 鸟的几何与 curl noise 风场

#### 4.8.1 3 三角形 V 形（照 three.js `webgl_gpgpu_birds` 的极简几何族）

```
          ●━━━━━━━━━━━●                  ← 两个翼尖（相对身体中心 ±w·s, ±wingRise·a）
           \             /
            \           /
             ●━━━━━━━━━●  ← 身体（短横条）
```

- 逐鸟 `s`（翼展缩放，逐鸟微抖）、`a`（扑动幅度）、`φ`（侧倾角）。
- ⛔ **扑动与侧倾都不进 Path 变换**（⛔ 不用 `save/rotate/restore`、⛔ 不用 `Matrix`），
  全部在**顶点坐标里算完**（§五）。
- 扑动只改 `wingRise`（翼尖相对身体的上下偏移）⇒ 这就是 §3.4 要的"振幅调制"的可读出口。
- 滑翔态：`wingRise → 0` 且翼**后掠**（`s` 减小、翼尖向后收）⇒ 一条窄横条。

#### 4.8.2 curl noise 风场（无散度 ⇒ 读作风，不是随机力）

2D curl noise 的闭式写法（**解析求导 ⇒ 精确无散度 ⇒ 热循环里只有几次三角函数**）：

```
ψ(p)   = Σ_i  A_i · sin( k_i · (p · d_i) + φ_i )          // d_i 是单位方向，φ_i 固定
B(p)   = ∇ × (0,0,ψ) = ( ∂ψ/∂y , −∂ψ/∂x , 0 )            // ⛔ 恒无散度（解析恒等式）
∂ψ/∂x  = Σ_i  A_i·k_i·d_ix · cos( k_i·(p·d_i) + φ_i )
∂ψ/∂y  = Σ_i  A_i·k_i·d_iy · cos( k_i·(p·d_i) + φ_i )
```

- ⭐ **为什么必须是 curl 而不是随机力**：随机力是**发散**的（各处独立推动）⇒
  鸟群读成"被风吹散的蚂蚁"；curl 场**无散度** ⇒ 鸟沿**流线**运动，群体整体被同一个大尺度涡带着走
  ⇒ 读成**风**。这是"风"与"乱推"的唯一可计算区别。
- **条数** `N_terms = 4`（✅ 原型实证 `NWIND = 4`，HTML 常量；方案原估量级 3–4 吻合）；
  `A_i / k_i / d_i / φ_i` 全部由**固定种子**生成
  ⇒ ⛔ 每帧随机（§三 的随机性纪律，见 §十三）。**原型实证：`NWIND = 4`**（HTML 常量），
  幅值 `windA = (0.5 + rand·0.8)·curlAmp`、波数 `k ∈ [3, 8]`、方向 `d` 与相位 `φ` 由种子 `27182818` 生成
  （`rebuildLayout()` 内）。P 表实证值：`curlAmp = 0.00080`、`curlDrift = 0.025`。
  ⚠️ **实现细节**：HTML 除 4 项 curl 涡外还有一项**主导横向平流**（`baseFx = 0.20·sin(y·0.0012 − t·0.06) + 0.07`），
  它才是打破对跖双群的主因；Kotlin 照抄这条组合，⛔ 只做纯涡项会恢复双群对跖。
- 风场随时间缓慢**平移**（`p · d_i` 里减去 `c·t`）⇒ 涡会真的在动，而不是原地抖动。
- ⛔ **不用 Reynolds 的 `wander`**：他的 `wander` 是给每只鸟一个**随机的 wander 目标点**再转向它，
  各鸟之间**无关联** ⇒ 群体读成"一群喝醉的鸟"，而且各向异性检验（§八 R2）会直接塌掉。

### 4.9 转弯侧倾（照 §3.3 的 StarDisplay 结论）

```
a_lat   = 横向加速度分量（⊥ 当前速度平面）
φ_target = atan2(a_lat , g)                            // g 取固定重力常数 g0
φ       ← rollIn  · (φ_target − φ)      当 |φ_target| > |φ|
φ       ← rollOut · (φ_target − φ)      当 |φ_target| ≤ |φ|
rollIn / rollOut = 2 : 1                 // ⛔ 滚入比滚出快（§3.3）
```

- ⛔ **不实现"侧倾导致掉高度"**（§3.3 的理由）：剪影下它把鸟群读成鱼群。
- `φ` 的最终用法 = **旋转翼形 + 让翼的可见面积随倾角变化**（倾得越狠，翼越像一条线）
  ⇒ 这就是 §二.3 说的"侧倾是唯一的姿态信息"的兑现处。
- ⚠️ `g0` 是**旋钮**：`g0` 大 ⇒ 同样的横向加速度给出更小的倾角 ⇒ 侧倾波在剪影上更弱。
  ⇒ T6 判倾角分布落在区间 + 负样本（`g0` 取极端值）。

- ⭐ **原型实证（2026-10-14）**：`g0 = 0.90`、`rollRatio = 2.00`（实现为 `tau = |φt|>|φ| ? 0.07 : 0.14` 的指数趋近，
  ⛔ 与 §4.9 的线性 `rollIn/rollOut` 形式不同但比例同为 2:1）、倾角钳制 **±45°**（T9 实测中位数
  LOW 4.5° / MED 2.8° / HIGH 2.7°，全部远低于 45° 上限 ⇒ 剪影读感正常、不过度侧倾）。
  风场幅值注释：**弯道倾角偏小的补偿手段已经用掉**（g0 从原 1.60 调低到 0.90 才让侧倾读得出来）
  —— 这条实测记录直接支持 §4.4 的“⛔ 不要在 φ 公式里另加补偿系数”之外的第二条路径：
  `g0` 本身就是合法补偿旋钮，Kotlin 侧必须把它做成可扫参数，⛔ 不得硬编码。

### 4.10 逐鸟巡航速差异与响应系数差异（⭐ 不做就会"原地呼吸然后僵住"）

```
cruiseK_i  ∈ [0.82, 1.18]        // 逐鸟巡航速倍率
w_i        = 1 + ξ_i ,  ξ_i ∈ [−0.15, +0.15]   // 三规则权重逐鸟微抖
resp_i     = k_resp · (1 + ζ_i) ,  ζ_i ∈ [−0.25, +0.25]   // 响应系数（加速度平滑）
```

- ⭐ **Reynolds 原文明说过的失效模式**：如果所有个体参数完全相同，
  群体会退化成**刚性结构**——先"原地呼吸"（净力反复抵消）然后**僵住**。
  这个失效模式**与规则权重是否合理无关**，只与"个体是否同质"有关。
- ⇒ **逐鸟差异是必需项，不是美化项**。T7 判：把 `cruiseK_i` 全部置 1 ⇒
  极化序参量 γ 的**时间方差塌到 0**（群体冻结），而正样本里 γ 必须**持续起伏**。
- ⛔ `resp_i` 的实现是**加速度的一阶低通**（不是速度低通）：
  低通加速度 ⇒ 重的鸟转向慢、快的鸟转向快 ⇒ 同一条转向指令产生**错峰**。

**原型实证（2026-10-14）**：`resetFlock()` 实际生成
`speedK ∈ [0.82, 1.18]`（`0.82 + rand·0.36`，恰好命中 §4.10 目标区间）、
`respK ∈ [0.75, 1.25]`（`0.75 + rand·0.50`）、`omegaK ∈ [0.92, 1.08]`（扑动频率抖动 ±8%）。
⚠️ **P 表里的 `cruiseJit = 0.08` 未被 speedK 消费**（死参数，见 §8.3），实际差异范围由 resetFlock 常量决定；
Kotlin 侧把 `cruiseJit` 从参数表删除、把 0.82/1.18 范围作为 Baseline 生成值 ⛔ 不得手抄。
另外 HTML 还实现了一项 §4.10 未写的机制——**扑动弱同步（Kuramoto）**：`flapPh` 与最近邻居相位差趋同
（`dph·min(1, dt·0.05)`），配合 ±8% 频率抖动保证 K < Kc 不全局塌缩（两轮实测 flap% 塌到 97% / 4% 的教训）；
⇒ Kotlin 侧**必须**保留扑动弱同步 + 频率抖动这一对机制，⛔ 只做单一频率 `sin` 会退化成“阅兵式”或“集体滑翔”。

## 五、渲染架构（本方案的核心）

> ⚠️ 本节每一条都来自**已在真机验收过的效果**（E43/E44/E46/E47/E48）与
> **已实测的 API 22 创维崩溃形态**，不是偏好。

### 5.1 ⛔ 为什么绝不能"一鸟一次 `drawPath`"

- **真机基线（已实测）**：创维 API 22 的 HWUI SIGSEGV 触发器 =
  「**大量互不相连的小矩形** + **无全屏操作**」。合并大基元安全。
- **项目自设硬门槛**：**30 op**（E47 §十 引述）。
- ⭐ **已知负样本**：E47 的雪若逐粒提交，HIGH 档 **1281 op = 上限的 43 倍**。
  本主题鸟数 600（HIGH）⇒ ⛔ 逐鸟提交 = **600 op = 上限的 20 倍**，
  ⛔ 且每一只都是互不相连的小三角 —— **正是那条已复现的崩溃形态的精确形状**。
- ⇒ **合批不是优化，是这个主题能不能跑的问题。**

### 5.2 ✅ 合批方案：每层一条 Path，顶点里做完变换，每层只 `fill` 一次

```
for L in 0 .. 3:                                  // 4 个飞行深度层，由远及近
    path[L].rewind()
    for i in layer[L]:                            // 该层的全部鸟
        屏幕坐标 = rotate(scale(birdVerts, s_i), φ_i) + (px_i, py_i)
                   // ⛔ flap 只改 wingRise、bank 只改 φ —— 全部在这里算完
        path[L].moveTo / lineTo / close            // 3 个三角形 = 9 个顶点
    canvas.drawPath(path[L], paint)                // ⛔ 每层恰好 1 次
```

- ⛔ **不用 `canvas.save/rotate/restore`**：每次 `save`/`restore` 都是一对 JNI + Matrix 状态压栈，
  600 只 × 4 层 = 数千次/帧 ⇒ 不可接受。变换在顶点坐标里做，代价是纯算术。
- ⛔ **不用 `Matrix`**：同上（且 Compose 侧要走 `Canvas.concat`，E46 的 `Canvas.concat` 已经踩过一次坑，
  见 `docs/technical-overview.md` §10.230）。
- ⛔ **不用 `clipPath` / `clip` / `RoundedCornerShape`**：⭐ **全项目禁物**，
  Android 5.1 真机**三次复现**的 hwui SIGSEGV，禁令范围是**整个** `clipPath`（不分圆角与否）
  —— 由 `SeasideTest` ① 与 `MoonlitSkySeaTest` ⑥ 源码扫描门锁死。本主题零裁剪需求（顶点已算好）。

### 5.3 ⛔ 为什么单调用批量顶点 API 不可用

| API | 级别 | 结论 |
|---|---|---|
| `Canvas.drawVertices(VertexMode, …)` | **API 29** | ⛔ **不可用**。本项目 `minSdk = 22` ⇒ 单调用的批量顶点 API 直接出局 |
| `Path` + `moveTo/lineTo/close` + **1 次** `drawPath` | API 1 | ✅ **本方案走这条** |
| `Canvas.drawBitmapMesh` | API 1 | ⚠️ 可用，但它是**位图网格**（要贴图）；本方案是**纯色剪影** ⇒ 用不上。<br>（E47 的大树风摆用它是因为那是**烘焙位图**的行位移，形态不同，⛔ 别照抄） |

⭐ **这一条是"不走 OpenGL"路线最硬的依据**：即使愿意引入 EGL，也换不到
`drawVertices` 级别的顶点批量（那要自己写 GL shader），而 §5.1 的崩溃触发器是
「未合批的小图元」—— **合批就已经解决了问题**，换后端解决不了任何额外的东西。

### 5.4 ⛔ 为什么不走 OpenGL / SurfaceView

1. **架构冲突**：既有契约是 `VisualizerRenderer` 的 `DrawScope.draw(frame, ctx)`
   （`VisualizerRenderer.kt`），工厂返回的就是这个类型；View 型旁路只有
   `isViewBased` 一条（`WorldGlobeRenderer` 用它承载 WebView），且旁路开启后
   `draw` **不再被调用**。⇒ GL 方案要么新开一条旁路（第三种形态），
   要么把 GL 挂进 `draw`（每帧创建/交换 EGL surface）。
2. **生命周期错配**：`onSurfaceCreated/onSurfaceChanged/onSurfaceDestroyed`
   与 Compose 的重组/进入退出**不同步**；E41 的教训是「WebView + three.js 在电视上死」，
   而 E43–E48 五套效果全部在 `DrawScope` 上验收通过。
3. ⛔ **收益为零**：崩溃触发器是"未合批的小图元"，§5.2 的合批已经把它解决。
   ⇒ **判定：走 `DrawScope` + Path 合批，不引入 GL 依赖。**

### 5.5 逐帧结构与 op 账（目标 8~12 条）

```
renderFrame(t):
    blit(B.sky)                    → 1 op   全屏（1.000 屏）
    blit(B.ground)                 → 1 op   地面带（视差 v1）
    blit(B.trees)                  → 1 op   树剪影带（视差 v2 < v1）
    for L in 0..3: fillFlockLayer(L) → 4 op  由远及近，每层一条 Path 一次 fill
    fillPerched()                  → 1 op   停栖鸟（画在树之后 ⇒ 读得出"在树上"）
    blit(B.nearTufts)              → 1 op   近景草丛（视差 v3 > v1，贴镜头）
    blit(B.grade)                  → 1 op   全屏（1.000 屏）
```

| 组 | 条数来源 | 铺屏来源 |
|---|---|---|
| 天幕 | 恒 1 | **1.000 屏** |
| 地面带 | 恒 1 | `0.20H × W`（**恰为 1/5 屏**，需求 ①） |
| 树带 | **2**（⚠️ 原型拆 `drawFarTrees` + `drawTrees` 两条 Path；与方案“恒 1”的差异见下注） | 树带高度 × W（原型 ≈ 0.04 屏） |
| **鸟群 4 层** | **4**（⛔ 与鸟数**无关**，这正是 §5.1 的全部意义） | 每只鸟的 3 个三角形面积和（**极小**，原型估 0.25 屏 @600 鸟） |
| 停栖鸟 | 1 | 极小 |
| 近景草丛 | 1 | 带宽 × W（原型估 0.05 屏） |
| 调色 | 恒 1（HTML `grade` 默认开） | **1.000 屏** |
| **合计** | **原型实测 11 op**（T1：`≤13 PASS`；隔档不随鸟数变 ⇒ §6.2 恒 1 成立） | **原型估 T6：LOW 2.39 / MED 2.47 / HIGH 2.55 屏** |

- ⛔ **铺屏是深度累加的 overdraw，不是"唯一像素"**（E48 §10.2 的口径警告原文适用）。
- ⭐ **本主题有两张全屏 op**（`sky` + `grade`）垫在首尾 ⇒ 命中 §5.1 说的"无全屏操作"反面的安全侧。
  ⚠️ **护栏**：砍降级项时 ⛔ **不许把 `sky` 一起砍掉**（那就失去唯一的全屏锚）。
- ⚠️ **版本注记（2026-10-15）**：HTML v2 比本表多拆 1 条 op —— 树带从“恒 1”拆成
  **远树（`drawFarTrees`，第 868 行）** 与 **近树（`drawTrees`，第 869 行）** 两条 Path（远树是做天际线纵深，
  近树承担停栖分支）。⇒ 原型实账 **11 op**（T1 上限 13 内的余量从 3 收窄到 2）。
  Kotlin 侧**照拆两条**还是**合并回 1 条**是 K5 的实现决策：合并省 1 op 但会把远树/近树的深度分层压扁；
  本方案注记保留原型拆分（同事先前 E47 的雪松也是“近树+远树”两条，见 §10.233）。

### 5.6 视差（需求 ②：地平线固定 + 极缓慢横向漂移）

- 地平线 `horizonY` **恒定** ⇒ ⛔ 不进 `Params`、⛔ 不受鸟群包围盒影响。
  （照 E47 D11/T12 的结构闸门形态：Kotlin 侧必须有护栏测试断言参数表里**没有**这个键。）
- 三条带的横向漂移速率 `v1 < v2 < v3`（地面 / 树 / 近景草丛），**量级差一个数量级**：
  慢到"盯着看十秒才确认它在动" ⇒ 这是"极缓慢"的量化落点。
  **原型实测（2026-10-15）**：`vGround=12 / vTree=6 / vTuft=22`（P 表 px 单位，滑杆范围 0~80/50/120），
  实际横向偏移 = 参数 × 各自缩放系数 × 30 px/s ⇒ 地面 ≈ 43 px/s、远/近树 ≈ 6~18 px/s、草丛 ≈ 119 px/s；
  「极缓慢」锚点由**树带 ~6 px/s** 承担（10 秒约 60px ≈ 屏宽 3.7%，"盯着看十秒才确认它在动"）。
  ⛔ Kotlin 侧照 §5.6 的 1:1 源区拷贝实现，速率换算口径与原型一致后锁 `BirdsFlockParallaxTest`。
- ⛔ **漂移必须用 `ImageShader(TileMode.Repeated)` 或 1:1 源区拷贝**（E47/E48 的先例），
  ⛔ **不得**每帧 `translate` + 画两张（那是 2 倍 op）。

### 5.7 热循环零分配（`VisualizerRenderer` 的性能红线）

| 项 | 口径 |
|---|---|
| soa 数组 | 全部 `FloatArray`：**HTML v2 实测名单** `px / py / vx / vy / accX / accY / flapPh / bank / dIdx / dSpd / speedK / respK / timer / omegaK`（14 条；⛔ `dIdx`/`dSpd` 在 `allocSOA()` 里**重复分配**两次，§8.3 C）。Kotlin 终名单由 K3 状态机审定（perch 状态按 `state / perchTree / perchSlot / timer` 补，权重若逐鸟化补 `wSep / wAli / wCoh`） |
| Paint | **一支填充 Paint**（逐层改 `color`）、**一支描边 Paint**（调试叠加用）⇒ ⛔ 不得每帧 `Paint()` |
| Path | 预分配 **5 条**（4 飞行层 + 1 停栖），逐帧 `rewind()` ⇒ ⛔ 不得每帧 `Path()` |
| 距离 | **比较 `d²`，⛔ 不 `sqrt`**；只有最终归一化才开方 |
| ⭐ `normalize(0,0)` 守卫 | `normalize(v)` 必须在 `\|v\|² < eps` 时**早退返回零向量**。⛔ **一个 NaN 会在一帧内毒化全群**：NaN 传播到邻居距离比较 ⇒ 该鸟的邻接集变空 ⇒ 它的 net 力变 NaN ⇒ 下一帧整群决策崩。**T8 = 5400 帧 NaN/Inf 必须为 0** |
| 容器 | ⛔ 零 `listOf` / `ArrayList` / `MutableList`（`PerfBudgetContractTest` 逐帧可达扫描会挂） |
| 字符串 | ⛔ 零字符串模板（逐帧可达函数内） |
| DrawScope 接收者 | 每个 `draw*` 函数**必须**是 `fun DrawScope.drawXxx(` ⛔ 漏掉接收者会**整体逃过**零分配扫描（E43 §4.9.4 陷阱 ①） |

### 5.8 时间步与相位推进

```
FIXED_DT   = 1/60 s
dtClamp    = 0.10 s          // ⛔ 帧间隔被系统打断时的截断，防止一步跳过整段
maxSubstep = 3               // ⛔ 最多 3 个子步；超出就丢掉余量（宁可慢放不追赶）
flapPhase  ← 在**渲染阶段**推进（⛔ 不是模拟阶段）
```

- ⚠️ **扑动相位在渲染阶段推进**是刻意的：扑动**不参与任何动力学决策**，
  放渲染阶段可以让模拟以任意倍率跑而不影响扑动的连续性。
- ⛔ **不得用 `frame.timeMs` 直接当相位**：切歌/静默帧会让时间跳变 ⇒ 扑动会瞬移。
  ⇒ 用**单调累加的内部相位**。

### 5.9 停栖（停树 → 再起飞）的渲染与遮挡

- 停栖鸟与飞行鸟**共用同一条 V 形几何与同一支 Paint** ⇒ ⛔ 不引入第二套绘制路径。
- 停栖鸟画在**树之后**（§5.5 的图层序）⇒ 读得出"在树上"。
- 起飞时**不是**"突然消失再出现"，而是**从停栖位起步、按 §4.1 的规则自然飞走** ⇒
  侧倾与扑动立刻接管 ⇒ 无缝。
- ⚠️ 树带只有一层 ⇒ 同一棵树上不同枝条的停栖鸟**没有前后遮挡**（同深的近似）。
  记为**已接受的近似** + 风险（§八 R1）。

⚠️ **原型偏差（Kotlin 迁移时必须决策）**：HTML v2 的 `drawPerched()` **没有**共用 V 形几何，
而是对每只栖鸟画一个**固定朝上小三角** `(x−3,y)→(x,y−8)→(x+3,y)`，且用**独立 fillStyle**
（`hsl(230,12%,8%)`，与飞行层最深色 `rgba(26,5,3)` 不同）⇒ 与“共用 V 形几何”契约不符。
⇒ Kotlin 侧二选一：**① 用与飞行同族的 `bakeBirdVertices` 几何 + 同一支 Paint 变色**（推荐，忠实 §5.9）；
**② 保留固定小三角**（省顶点计算，但停栖鸟在 zoom 裁块下与飞行鸟形态不一致）。
⚠️ 停栖鸟**必须仍然高于地平线**（G4 门禁 + `perchMaxY` 过滤低位枝）；固定三角的高度 8px 是 R1
“1600×900 上是否肉眼可读”的下界参考值（原型 8px 在 full 缩略图上≈不可读，裁块判读见 §13.6）。

### 6.1 鸟数按画质档

| 档 | 鸟数（**设计目标**） | 说明 |
|---|---|---|
| LOW | **200** | ⛔ **LOW 档必须可选**（§十二 的 `needsParticleBudget = false` 合法性论证） |

## 七、音频映射（周边环境，随包围盒伸缩）

**输入只用现成字段，⛔ 音频分析层零改动。**

- ⛔ **吃律动通道**（线性 `bass / mid / treble / energy`），⛔ **不吃显示通道** `spectrum`
  （`AudioFrame.kt` 的双通道铁律：显示通道已 gamma 压缩，拿它驱动律动会把强弱差异压扁）。
- ⭐ **核心纪律：音频只驱动「周边环境」，⛔ 不直接驱动鸟的行为决策。**

  音频若改这些，仿真会变成"随音乐抽搐"，且**不可复现**、harness 的逐位复现判据会永远变红。

| 通道 | 消费点 | 语义 | 系数 |
|---|---|---|---|

| `energy` | **地面/草丛漂移速度** | 响 ⇒ 地面走得快一点（与鸟无关，只给参照速度） | ⛔ 原型 0 实现，Kotlin 侧回填 |
| `mid` | **地平线暖雾浓度** | 人声段 ⇒ 近地大气厚一点 | ⛔ 原型 0 实现，Kotlin 侧回填 |
| `treble` | **天顶亮度带 + 鸟的逆光边** | 高频 ⇒ 天更亮、鸟的暗边更透 | ⛔ 原型 0 实现，Kotlin 侧回填 |
| `sectionEnergy` | **风的长周期基线** | 段落级慢变，⛔ 不做逐拍 | ⛔ 原型 0 实现，Kotlin 侧回填 |
| `pulse` / `beat` / `bpm` | **⛔ 不用** | 本主题无节拍语义；用了就与 E47/E48 的"纯氛围克制"分裂 | — |

⭐ **"随包围盒伸缩"的量化落点**：harness 必须输出
**「`bass` → `windAmp` → 群体包围盒宽度」这条链的相关性与时间滞后**
（⛔ 见下方注记：**原型 0 实现不可测**，此量归 Kotlin 侧 `BirdsFlockAudioGateTest` 真值），
⛔ 不得只报"映射接上了"。另外必须有一条**无声零漂移**判据：
推进 `⟨n⟩` 帧在 `bass=0` 下，各通道 `max|Δ| = 0` 且**画面仍在动**（风有纯时间基线）。

⚠️ **HTML 原型状态（2026-10-15 核对，⚠️ 重要）**：音频映射在本原型中是 **placeholder**——
`kBass / kEnergy / kMid / kTreble / audioOn` 只有参数表 + 滑杆，**消费逻辑为 0**（§8.3 A 表）。
原型能验的只有「滑杆可调、切 `audioOn` 不崩」；**四条通道的相关性/滞后/无声零漂移判据在原型侧无数据**，
只能在 Kotlin 侧四通道接线后由 `BirdsFlockAudioGateTest` 与真机验证。⇒ §10.2 第 19 项**不回填原型数**。

### 8.2 R6 长条目：⭐ `postFx` 的三段式（照 `TripodFogRenderer`）

本主题的暗角与颗粒**烘进同一张全屏 `grade` 位图**（1 次 blit）⇒ 基类那一路必须**恒关**，
但 `FxCoverageScanTest` 的判据 A 只认 `override val postFx = PostFx(…)` 里的**裸 `f` 数字字面量**：

- ⛔ **只写 `override val postFx = PostFx(vignette = <x>f)` 而不覆盖 `vignetteOverride`** ⇒ 基类那一路暗角照画
  ⇒ 与烘进位图的暗角**叠加** = **双暗角、四角死黑**，且每帧多一次全屏 pass（+1.000 屏）。
- ⛔ **写 `PostFx.NONE`** ⇒ `postFxRe` 匹配不到 ⇒ `covered` 收不了它
  ⇒ 门禁判「本类未覆盖后处理」⇒ 只能进 `exempt`（E47 走的就是这条，见 R5 表）。
  ⚠️ 这**不是错的**，两条路都合法；但**必须二选一且与 `covered`/`exempt` 的归属一致**。
- ✅ **本方案选定三段式**（理由：与 E46/E48 同形，便于"降级杠杆砍调色层"时统一处理）：

  ```kotlin
  override val postFx = PostFx(vignette = 0.10f)          // ① 必须是裸字面量（门禁只认这个形式）
  override fun vignetteOverride(fx: FxFrame): Float = 0f // ② 恒关基类那一路
  ```

- ⭐ **`postFx` 那一行的三重身份**（照 `TripodFogRenderer` 的 KDoc）：
  ① `FxCoverageScanTest` 认定"走了基类后处理"的**唯一**依据；
  ② `needsDamageCoalescer` 的输入（`vignette > 0` ⇒ MED/HIGH **不**补脏区合并占位）；
  ③ 静默帧的锚。
  ⛔ **不要因为"反正逐帧被覆盖成 0"就写成 `0f` 或具名常量**（具名常量门禁立刻红；
  写 `0f` 会让 ② 翻案 ⇒ MED/HIGH 各多一次全屏填充）。
- ⛔ `vignette = 0.10f` 里的 `0.10` 与 `grade` 位图里烘的暗角强度**必须是同一个数**（两处口径一致）。

> ⚠️ **D1–D2 是 Kotlin 落地期（K4/K5）的偏差**，此前只写在代码注释里、本节漏记，2026-10-15 补录；

**D1 现象**：grade 调色层的暗角与原型不一致（原型是"内圆暖光 + 外圆暗角"两段径向）。
**根因**：Android 只有**单圆** `RadialGradient`，没有双圆径向渐变 API。
**修法**：收敛为单圆三停点近似（中心 0.02 暖 → 0.55 透明 → 1.0 黑 0.24），边缘 α 与
`postFx.vignette = 0.24f` 同数（`BirdsFlockBakes.bakeGrade`）。
**复验口径**：`MoonlitAudioTest` 的 `vignetteOverride` 覆写名单 + 目视（暗角不得叠两遍）。

**D2 现象**：真机（高 DPI）上"树 / 远树 / 草丛细到看不见"，读成一排细棍。
**根因**：原型的线宽是 **1600×900 的设计 px 定值**（干宽 6~10px、枝宽下限 1.2px、叶半宽 1.1px），
搬到 1080p / 1220p 上既没乘 `s = h/900`、绝对值也太细。
**修法**：① 树高 / 远树尺寸 / 尺寸锚点全部乘 `s`；② 干宽系数 0.030+0.016 → 0.045+0.024、
远树干宽 ×1.4、枝宽系数 0.075 → 0.13（下限 1.2 → 2.0s）、叶半宽 1.1 → 2.0s。
**复验口径**：真机截图裁块（owner 判读）。
⚠️ 本轮**只治了"细"**——"看不见"的真根因是 D3，加粗救不了整条带消失。

**D3 现象**（2026-10-15 真机截图 2712×1220，owner 原话）：**①「树显示不出来」；
②「远处的草是个竖棍」；③ 近景草丛整条看不见；④ 栖鸟悬在半空**。
**根因**：`BirdsFlockRenderer.drawBand` 只挪了 `drawRect` 的 `topLeft`，而 Compose 的
`drawRect(brush, topLeft, size)` **不会**把着色器一起挪 —— `CanvasDrawScope.drawRect-AsUm42w`
把 `topLeft/size` 算成矩形后直接 `Canvas.drawRect(l, t, r, b, paint)`，`ShaderBrush.applyTo`
建着色器时**不带任何 local matrix**（`ui-graphics` 字节码逐条核对）⇒ 着色器锚死在**画布原点**。
于是（`TileMode.Repeated` X / `Clamp` Y）：
- `topLeft.y = hY − pad > 0` ⇒ 着色器按**画布 y** 采样，落到 tile 之外 ⇒ `Clamp` 把 tile
  **最后一行铺满整条带**；
- `topLeft.x = −off` ⇒ 只改了矩形范围、**图案一点不动**（三条带的横向视差从未生效）。

逐条对上真机症状：远树带（tile 88px，最后一行 = 三角底边那一行）⇒ **一排等高竖棍**；
树带（tile 261px，最后一行在树根之下 = 全透明）⇒ **整条消失**；草丛带（tile 244px，
最后一行在叶尖之下）⇒ **整条消失**；栖鸟按 `treeOff` 挂在枝尖 ⇒ 树没画出来 ⇒ **悬空**。
像素实测佐证：竖棍恰好只占 `y ∈ [888, 976]`（= 远树带矩形的上下沿，地平线 976），
对比度沿 y 基本恒定 —— 若是正常渲染，内容应止于三角尖（≈914）并向上收窄。
**修法**：`drawBand` 改为 **`nativeCanvas.translate(−off, y)` 平移画布**（画完立刻反向平移还原）
⇒ 着色器连同矩形一起落到带上沿，采样行 = tile 的 `0..dh`（正确），横向视差同时恢复生效。
⛔ 不用 `save`/`restore`（本文件红线 3）、⛔ 不用 `setLocalMatrix`（E43 真机实测退化成 identity）；
⛔ 不改 op 数（仍 1 op/带 ⇒ 逐帧结构恒 11 op）。
连带两处：`treePad` `160s → 250s`（按枝尖几何上界
`(T−B·j)/2 + (T+B·j)·yf/2 + cos(a)·T·lf·0.85 + T·lf·0.26 ≈ 220` 推导）、
`treeTileGroundPad` `0.16 → 0.20` 带高 —— 原值会把最高那棵树的**上段主干与枝杈烘到 tile 之外**。
**复验口径**：`BirdsFlockRenderSourceGateTest` 新增两条（"带子定位必须平移画布而不是挪 topLeft"
+ 负向自证"旧写法样本必须判红"）锁住机制；真机复验 = owner 在手机上装
`NASMusicTV-release-v2-38-12.apk` 后判读"地平线上是不是树形 / 树上有没有鸟"。
**影响面**：⚠️ **E47 雪松的 `drawBand` 是同款代码**（`SnowCedarRenderer.kt:483`），同样"着色器锚画布原点"
⇒ 它的三条带同样没在滚、i≥1 的云层与远/近面纱带同样被 Clamp 折成一条平横带；因 E47 的带是**低对比雾霭**
（一条平雾读起来仍像雾），真机上没暴露。**2026-10-15 经 owner 裁决一并修**（修法同款、op 数不变）
⇒ E47 的带会**回到设计 y 位置并开始真的滚动**（旧写法下按"位图行号"落位，比设计位置整体上移 `y`），
owner 需重看 E47。
**连带（视差速度对齐）**：`vTreePx/vTuftPx` 是 **1600×900 的设计 px 系数**，调用点补乘 `scale() = h/900`

### 11.4 真机验收清单（所有者执行）

1. **第一读感是不是"一群鸟在飞"** —— ⛔ 试读成"一团毛球"/"一堆乱窜的粒子"/"鱼群"即判失败（§3.3 的掉高度正是鱼群的成因）。

   ⛔ 不是"树上有黑点"。⚠️ **本条预留"不通过"的余地**：若底部 1/5 带的尺寸撑不住，降级方案 = 盘旋代替站定（§十四 O2）。
5. **停栖鸟与飞行鸟分不分得开**（§二.3：⛔ 停栖不得比飞行更深）。
6. **地面的横向漂移是"极缓慢"还是"已经动了"**（需求 ②）—— ⛔ 后者即失败（会抢主体、且在电视上更明显）。
7. **地平线的直线是"远景"还是"尺子线"**（R12）。
8. **暖色荒野与 E48 的暖红落日在同一台电视上分不分得开**（R9）。
9. **帧率沿用 E44 的 `--fps` 采样口径。**

## 十三、原型使用说明

> ✅ **本节已与原型 `SLIDERS` 表逐项对账（2026-10-15）**：路径、滑杆、按钮、HUD 均已建成。
> ⚠️ **对账结论（2026-10-15 修订）**：分组名称与下表一致（实为 10 组）；§8.3 A 的 6 个死参数

> ⇒ Kotlin 侧控件以**真实消费的参数**为准，⛔ 不要照抄下表未删前的滑杆条数。

### 13.1 原型

- **文件**：`docs/e49-birds-flock-preview.html`（纯 Canvas 2D，**1600×900** canvas，⛔ 无 WebView / three.js / OpenGL）。
- **门禁解锁**：点画面 ⇒ 出右栏与 HUD（照 E47/E48 的同款交互）。
- **控制台命名空间**：`window.__E49`，内含 `P`（参数表，**唯一真值来源**）、`TIERS`（档位表）、
  `SLIDERS`（滑杆表）、`B`（烘焙位图）、`L`（布局量）、`layout()` / `rebuildLayout()` / `resetFlock()`、
  `stats(n)` / `profile()` / `beatScan(n)` / `selfTest()`。
- ⛔ **原型不得出现逐帧随机数**（所有 hash 吃 `(i, 固定种子)` ⇒ 同一次进入画面**逐位可复现**，T1 判这条）。

### 13.6 截图驱动（判读时刻由页面 `beatScan` 现算，⛔ 不写死秒数）

```bash
# ✅ 已建成（真浏览器 Edge + CDP 9349）
node docs/archive/verification/scripts/e49_flock_driver.mjs phases        # 判读帧（由 beatScan 现算时刻）

```

- ⚠️ `target` 取 `birds` / `tree` / `ground` / `field`（`field` 用来看 curl 场流线）。
- 输出走**最近邻**（`imageSmoothingEnabled = false`）：本主题的停栖鸟与鸟翼形在整帧缩略图上
  ⛔ **必然**得出错误结论，必须用裁块判读。
- ⚠️ **CDP 端口 9349**（⛔ 不复用 9333 / 9334 / 9336 / 9337 / **9338**（e48））。
- 输出到 `output/e49_frames/`（gitignored）。
- ⚠️ **判读帧必须互相不同**：E48 的教训是两个判读时刻撞在同一 `t` ⇒ 两张截图 SHA-256 逐字节相同
  ⇒ 那是"同一个画面挂两个名字"，**不是两个独立判读位**。⇒ driver 必须对每张判读帧算 SHA-256
  并**断言两两不同**（§10.2 第 21 项）。
